## 후속 설계

### A 일정의 바쁨 의미와 갱신 상태

Google의 바쁨 속성과 앱 일정의 가용 시간 차단 여부를 별도로 저장한다. 현재 Google 동기화는 시간 확보 안 함 일정의 저장을 건너뛰므로, 해당 일정을 내 달력에 표시하면서 그룹 가용 시간을 차단하지 않는 데이터 모델이 필요하다. 기존 장기 일정은 기간만 보고 자동 제외하지 않는다.

구성원별 마지막 동기화 시각, 연결 오류 여부, 사용자가 가능 시간을 확인한 시각을 제목 없이 반환한다. 일정 미등록·동기화 지연·본인 확인 완료를 분리하고 후보 옆에서 보여준다. 시간표 RPC의 현재 `confirmed` 필드는 확인 상태의 근거로 사용하지 않는다. 운영 오류가 있어도 기존 일정을 지우거나 해당 구성원을 새로 ‘가능’으로 추정하지 않는다.

### B 약속의 참여자와 변경 및 확정

계획 참여자를 별도 테이블로 저장하고 기본 선택은 현재 그룹 구성원으로 제공한다. 장소 화면은 선택된 참여자의 이름을 가져오되 실제 출발지는 각자 확인한다. 여행은 출발·귀가 일시와 숙박일 수를 함께 표시하고 실제 기간을 공통 시간 검색에 적용한다.

서버의 제안·확정 절차는 현재 구성원과 개인 일정 및 이미 확정된 계획을 정확한 시간 구간으로 다시 비교해야 한다. 제안은 충돌이 있어도 가능하게 하되 경고한다. 확정은 현재 상태와 응답을 반환하는 사전 확인 후, 변경된 데이터가 있으면 다시 확인하도록 한다. 사용자 확인 이후 경쟁 상태를 막기 위해 최종 확정은 그룹 단위 잠금과 버전 확인을 포함한 DB 트랜잭션에서 처리한다. 다른 그룹의 확정 일정이 개인 시간을 차단해야 하는지도 함께 결정해야 한다. 현재 계산은 해당 그룹의 확정 계획만 반영한다.

제안자는 본인의 미확정 제안을 수정·삭제하고, 생성자는 확정 계획의 변경·취소를 관리하는 정책을 권장한다. 시간·참여자 변경은 기존 응답을 보관하되 재응답 대상으로 표시한다. 취소는 기록을 남기는 상태 변경으로 하고 가용 시간 계산에서 제외한다. 상태 제약·RLS·가용 시간 RPC를 함께 바꿔야 하므로 이번에 단순 삭제 버튼만 추가하지 않았다. 실시간 전달은 제목을 포함하지 않는 그룹 변경 알림과 재조회로 설계한다. 현재 탭 복귀 시 재조회는 즉시 푸시 갱신을 보장하지 않는다.

### C 출발지 선택과 지역 없이 장소 찾기

출발지는 장소 검색 후보의 이름·주소·좌표를 확인하거나 지도 핀·본인 GPS로 확정한다. GPS는 버튼을 누를 때 요청하며 권한 거절 시 검색을 계속 사용할 수 있게 한다. 다른 참여자의 위치를 본인 GPS로 채우지 않는다. 좌표와 표시명은 이번 검색에만 사용하고 그룹에 저장하지 않는 기존 원칙을 유지한다.

‘특정 지역’과 ‘중간 지점’ 모드를 구분한다. 1명은 출발지 주변 탐색, 여러 명은 여러 후보 지역을 실제 이동 시간으로 평가한다. 사용자가 최장 이동 시간·참여자 간 편차를 우선할지, 총 이동 시간을 우선할지 선택하도록 한다. 좌표 평균은 탐색 시작점으로만 사용할 수 있고 공정한 이동 시간의 근거가 되지는 않는다. API 호출량·미확인 경로·지역 후보 수를 제한하고 결과에서 추천 근거를 표시한다.

### D 최초 로그인과 Calendar 연결 운영 확인

Supabase의 Google OAuth 설정과 앱 서버의 `GOOGLE_CLIENT_ID` 및 `GOOGLE_CLIENT_SECRET`이 같은 OAuth 클라이언트를 사용하는지 확인해야 한다. 로그인에서 얻은 Google 갱신 토큰을 앱 서버에서 재사용하기 때문에 이 구성이 다르면 다시 연결 요구가 생길 수 있다. 이는 운영 설정 조사 후보이며 제보의 확정 원인은 아니다.

신규 계정에서 앱 로그인 횟수와 Calendar 동의 횟수를 각각 기록하고, 콜백 직후와 새로고침 후의 세션·연결·일정 조회를 확인한다. Calendar만 실패했을 때 소셜 로그인을 다시 요구하지 않아야 한다. 권한 거절·부분 동의·복구 취소·세션 만료·다른 Google 계정 선택도 확인한다. 로그에는 처리 단계·성공 여부·오류 분류만 기록하며 코드·토큰·비밀번호는 남기지 않는다.

쿠키 전달 방식은 [Supabase SSR 공식 안내](https://supabase.com/docs/guides/auth/server-side/creating-a-client?environment=client-component)를 참고했다. 계정 식별은 [Supabase identities 안내](https://supabase.com/docs/guides/auth/identities)를 참고하되 기존 코드의 식별자 사용을 반복 로그인 원인으로 단정하지 않는다.

## 검증과 운영 잔존 데이터

인증 회귀 8개를 추가했고 기존 장소 API 검사에는 자유 키워드와 빈 직접 입력 검사를 포함했다. DB 가용 시간 검사는 보고서의 10월 31일 사례를 재현해 확정 전후 총 가능 시간과 추천 수 및 겹침 제거를 확인한다. 이 DB 검사는 브라우저 이벤트 전달의 검증을 대신하지 않는다.

로컬 단위 및 DB/RLS 테스트 43개, 타입 검사와 린트가 통과했다. 프로덕션 빌드는 검증용 공개 Supabase 설정으로 통과했다. 실제 서비스 연결 성공을 의미하지 않는다. 실제 계정 로그인, 외부 API 실호출, 휴대폰 화면과 키보드는 별도 검증이 필요하다.

보고서에 기록된 QA 그룹의 클론 멤버와 10월 18일 제안 및 10월 31일 확정 계획은 그대로 남아 있다. 기존 개인 일정과 운영 Google Calendar는 변경하지 않았다. 그룹 및 계획 관리 기능을 구현한 뒤 해당 테스트 데이터만 정확히 식별해 정리해야 한다.
