# 5총사 시간 일정 배포

## 적용 순서

1. 운영 DB를 백업한다. 기존 설치에서는 현재까지 적용된 마이그레이션을 확인한 뒤 `supabase/migrations/202610080001_google_auto_sync.sql`을 적용한다. 신규 설치는 날짜 순으로 전체 마이그레이션을 적용한다. 기존 일정·그룹·연결은 삭제하지 않는다.
2. 기존 설치에도 `supabase/migrations/202610120001_calendar_realtime.sql`을 추가 적용한다. 본인 일정 RLS를 유지한 채 DB 변경 알림을 활성화하며, 미적용 시 기존 화면 자동 동기화로 동작한다. Vercel 환경변수를 아래와 같이 설정하고 재배포한다. 이 저장소에는 실제 비밀키를 포함하지 않는다.
3. Supabase Google 로그인 제공자의 OAuth 클라이언트와 서버의 `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`을 동일한 웹 클라이언트로 설정한다. Supabase Auth 콜백 URI와 서비스 도메인의 `/auth/callback` 허용 URL을 유지한다. 기존 `/api/google/callback` 허용 URI도 이전 연결 복구용으로 유지할 수 있다.
4. Supabase Auth에서 Google 제공자를 켜고 이메일·비밀번호 제공자를 끈다. 단, 기존 이메일 계정이 있다면 Google identity를 먼저 해당 사용자에 연결해야 데이터 접근이 유지된다. OAuth 제공자를 끄는 작업은 코드를 배포하기 전에 운영 콘솔에서 확인해야 한다.
5. 최초 Google 로그인 시 Calendar 이벤트 권한과 오프라인 접근에 동의한다. 서비스는 로그인 콜백에서 갱신 토큰을 암호화해 저장한다. 일반 로그인은 동의 화면을 강제로 요청하지 않고 기존 Calendar 토큰을 유지한다. 기존 토큰이 없거나 재인증이 필요한 오류가 확인된 경우 새 토큰을 저장한다. 토큰이 발급되지 않았거나 권한이 부족하면 로그인 상태를 유지한 채 ‘연결 복구’에서 명시적으로 다시 동의한다.
   - 다른 기기 로그인 직후 복구 경고가 반복되면 위 3번의 OAuth 클라이언트 일치 여부를 먼저 확인한다. 서버의 `Google token refresh failed` 로그는 HTTP 상태와 허용된 오류 코드만 기록한다. `invalid_client`·`unauthorized_client`는 운영 인증 설정을, `invalid_grant`는 토큰 무효화·만료 및 발급 클라이언트 불일치 가능성을 확인한다. 429·5xx는 재인증 대신 기존 토큰으로 자동 재시도한다. 토큰·시크릿이나 Google 응답 원문은 로그에 추가하지 않는다.

6. 그룹 초대 검색 배포 시에는 `supabase/migrations/202610160001_invite_search.sql`을 먼저 적용한다. 기존 프로필 RLS를 변경하지 않고, 그룹 생성자만 이름·이메일로 20명씩 검색한다. 프로필 이름을 아직 설정하지 않은 가입 계정도 이메일로 검색된다. 마이그레이션 미적용 시 검색 오류가 표시된다.

## 환경변수

| 변수                                                     | 용도                                                                                               |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| NEXT_PUBLIC_SUPABASE_URL / NEXT_PUBLIC_SUPABASE_ANON_KEY | 기존 Supabase 설정                                                                                 |
| SUPABASE_SERVICE_ROLE_KEY                                | 서버 전용 Google 연결 저장 및 동기화. NEXT_PUBLIC 접두사 금지                                      |
| NEXT_PUBLIC_SITE_URL                                     | 실제 서비스 origin, 예: https://5guys.example.com                                                  |
| GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET                  | Supabase Google 로그인 제공자와 **같은** 웹 OAuth 클라이언트. 다른 클라이언트이면 갱신 토큰을 사용할 수 없음 |
| GOOGLE_TOKEN_ENCRYPTION_KEY                              | 32바이트 난수의 base64. 토큰 암호화에 사용하며 변경하면 재연결 필요                                |
| CRON_SECRET                                              | Vercel 예약 동기화 인증용 충분히 긴 난수                                                           |
| OPENAI_API_KEY                                           | 서버 전용: 근무표 이미지 분석 및 장소 설명. API 프로젝트의 크레딧·사용 한도 확인, NEXT_PUBLIC 접두사 금지 |
| KAKAO_REST_API_KEY                                       | 국내 장소·출발지 검색 및 Kakao 공개 대중교통 경로 조회. 카카오맵 사용 설정 ON 필요                    |
| KAKAO_MOBILITY_API_KEY                                   | 자동차 길찾기 API                                                                                  |

암호화 키 생성 예: `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"`. 생성 결과를 Vercel 비밀 환경변수로 저장한다. 로그·Git·공개 채팅에 남기지 않는다.

## 동작 범위와 운영 확인

- 한국 시간(Asia/Seoul), 개인별 근무 기호·별칭·시간, 자정 넘김, 시간 단위 복수 일정, 일/주/월 반복 일정(최대 52회).
- 근무 유형 변경은 과거 일정에 소급 적용되지 않는다. 사진에서 인식한 휴무는 바쁜 일정으로 저장하지 않는다. 기존 수면·휴식 일정은 유지된다.
- 그룹 가능 시간은 각자의 `planner_events`와 확정된 그룹 계획에서 자동 계산한다. 별도의 날짜 확인 체크박스는 없다. 일정이 하나도 없는 날은 24시간 가능으로 표시되므로 일정 최신 상태를 확인해야 한다. 그룹 가능 시간 RPC에는 개인 일정 제목·근무 종류·이메일을 포함하지 않는다.
- 그룹 월간 달력은 날짜별 공통 가능 시간 합계를 보여주고, 날짜 선택 시 구성원별 30분 단위 시간표를 표시한다. 구성원 누구나 여행·약속 날짜 후보를 제안하고 투표할 수 있으며 그룹 생성자가 확정한다. 추천 장소를 그룹 계획에 저장하는 것도 생성자만 가능하다. 확정된 계획은 해당 그룹의 가능 시간에 반영되지만 개인 Google Calendar에 자동 등록하지는 않는다.
- 기존 날짜형 일정은 보존되어 스케줄 화면에서 확인 가능하다. 시간이 없는 근무는 임의로 변환하지 않는다. 기존 work_patterns의 유효한 시간 매핑만 신규 유형으로 가져온다.
- Google 기본 캘린더를 양방향 동기화한다. 최초 적재는 과거 90일~미래 366일이며 이후 변경분은 Google syncToken으로 가져온다. 토큰 만료(410) 시 전체 재조회한다. 반복 이벤트는 개별 발생 일정으로 DB에 적재한다. 서비스에서 만든 반복 일정도 Google에는 개별 발생 일정으로 반영되므로 Google 고유 반복 규칙과는 별도로 보인다.
- 화면은 DB 데이터를 먼저 표시한다. 대시보드 진입·화면 사용 중 2분 간격·앱 일정 변경 시 백그라운드 동기화한다. 최초 연결 상태 조회 실패 후에도 주기적 조회를 유지하고, 화면 복귀·창 포커스·네트워크 복구 시 다시 확인한다. Google 웹훅이나 다른 기기가 먼저 변경을 반영했을 수 있으므로 동기화 결과가 0건이어도 화면 캐시를 갱신한다. 정상 연결 시 마지막 자동 업데이트 완료 시각을 표시한다. Google 웹훅 알림으로도 변경분 처리를 시작한다. 웹훅 채널은 만료 전에 갱신하고 누락된 변경은 하루 한 번 UTC 18:00 예약 작업으로 복구한다. 예약 작업은 가장 오래 동기화하지 않은 10명까지 처리한다. 사용자 증가 시 큐·작업 분할이 필요하다.
- Vercel Hobby cron은 하루 한 번까지 가능하다. 웹훅 수신이 실패하거나 앱을 열지 않으면 다음 예약 복구까지 반영이 지연될 수 있다. 웹훅은 HTTPS 운영 도메인에서만 검증할 수 있다.
- 근무의 수동 등록·순환 일괄 등록은 제공하지 않는다. 근무 유형별 시간 매핑은 이미지 분석 결과 해석을 위해 유지하며, 근무 일정은 사진 분석 결과를 확인한 뒤 저장한다. 기존 근무 일정은 보존한다.
- 동시에 변경된 일정은 덮어쓰지 않고 충돌로 표시한다. Google 버전 적용 또는 내 수정본 별도 보관을 선택한다. 연결 갱신은 동일 Google 계정으로 제한한다.
- 근무표 분석은 사진 업로드 → OpenAI가 주간·월간·임의 기간의 전체 날짜·기호 분석 → 등록된 근무 유형 자동 매핑 → 결과 달력에서 수정·확인 → 추가 저장. 연도·날짜를 판독할 수 없으면 결과 화면에서 기간과 날짜를 보정한다. 최대 62일이며 월·연도 경계를 유지한다. Google Vision OCR은 사용하지 않는다. 광고가 포함된 전체 사진에서도 잘못된 결과가 나올 수 있으므로 저장 전 확인한다.
- 같은 날짜의 기존 근무가 있으면 재등록을 막는다. 기존 근무와 약속을 덮어쓰지 않는다. 휴무도 기존 근무를 삭제하지 않는다.
- 장소는 Kakao 실제 검색 결과 중 최대 3곳, 참여자 최대 8명. 자동차는 Kakao Mobility, 대중교통은 Kakao 공개 API를 사용하며 ODsay 연결은 사용하지 않는다. 이동시간 미조회·불완전한 구간 데이터는 0분으로 처리하지 않는다. 모든 참여자의 이동시간이 확인된 후보만 시간 기반 추천 순위와 AI 설명 대상이 된다. 미확인 후보는 별도로 표시하고 참여자별 카카오맵 길찾기 링크를 제공한다. 출발지는 저장하지 않는다.
- 장소 영업시간·예약 가능성, 미래 출발시각의 교통·막차, 국내 여행 숙박/여정 최적화는 제공하지 않는다. 장소 추천은 후보지 비교 기능이다.

## 검증

월 캐시·인접 월 미리 조회 동작 및 지도 서비스별 실제 구현/키 설정/미구현 범위는 [사용 가이드](USAGE.md)에 정리했다. 앱 내 지도 렌더링은 아직 없으며, 장소 검색·자동차·대중교통 조회는 Kakao로 통일했다. 기존 ODSAY_API_KEY는 더 이상 필요하지 않다. 신규 DB 마이그레이션은 이 API 전환에 필요하지 않다.

`npm test`: 날짜·야간근무·OCR 검증, 실제 PostgreSQL 엔진(PGlite)에서 마이그레이션/RLS/그룹 권한 검사.

`npm run lint`, `npx tsc --noEmit`, `npm run build`.

일정 편집 모달의 로컬 브라우저 검증: 빌드 후 `npm exec --yes --package=@playwright/test --package=esbuild -- node test/browser/planner-modal.cjs`. Windows의 설치된 Edge를 headless로 사용하며 1440×900, 390×844, 320×568에서 중앙/전체 화면 배치, 축소된 화면의 저장 버튼, Esc·뒤로 가기 초안 복원, 저장 오류 복구와 상세→수정 전환을 검사한다. 실제 컴포넌트와 빌드 CSS를 사용하지만 일정 조회·저장은 테스트 데이터와 메모리 mock으로 대체한다. 결과 이미지는 `work/editor-*.png`에 생성한다. 실제 iOS/Android 가상 키보드는 별도 검증 대상이다.

모바일 화면 전환 검증: 같은 빌드 후 `npm exec --yes --package=@playwright/test --package=esbuild -- node test/browser/motion.cjs`. 실제 대시보드·전환 패널·달력과 빌드 CSS로 390px/320px의 메뉴·월 이동 방향, 빠른 연속 이동, 메뉴 입력값 유지, 비활성 화면의 입력 차단, 가로 넘침과 동작 줄이기를 확인한다. 인증·백엔드와 개별 도구 내용은 mock으로 대체한다.

실환경에서 확인할 항목:

- 두 계정이 같은 그룹일 때 다른 계정의 planner_events와 기존 schedules 직접 조회가 차단되는지 확인.
- 기존 이메일 계정의 Google identity 연결 상태와 Google Calendar 권한·갱신 토큰을 운영 DB와 OAuth 콘솔에서 확인. 이메일 로그인 비활성화 전에 데이터 소유 계정 매핑을 점검.
- Google 웹훅 채널 등록/갱신과 이벤트 변경 알림 후 DB 반영, 만료 토큰 410 재적재, 웹훅 중복 수신 시 중복 일정이 생기지 않는지 확인.
- Google에서 생성/수정/삭제 → 가져오기, 서비스에서 생성/수정/삭제 → Google 반영, 양쪽 동시 수정 충돌 확인.
- 근무표 이미지 분석: 광고 배너를 제외한 동일 달력에서 날짜·표기·시간과 OpenAI 사용 토큰 확인. 실제 교대달력 스크린샷을 확보하면 광고/테마/월 경계별 회귀 샘플 추가.
- 장소·자동차·대중교통 키별 실호출, 검색된 출발지가 의도한 역/장소인지 확인.

현재 저장소에는 운영 Supabase 스키마 전체와 실제 근무표 이미지가 없어 테스트용 기존 스키마 및 구조화된 결과 샘플로 검증한다. 운영 데이터·외부 서비스 결과의 검증을 대체하지 않는다.
